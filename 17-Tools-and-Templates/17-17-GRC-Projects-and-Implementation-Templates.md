# 17.17 GRC Project and Implementation Templates

## Part 1 – GRC Project Charter

A GRC project charter formally defines the purpose, scope, objectives, governance structure, responsibilities, deliverables, assumptions, constraints, and success criteria of a Governance, Risk, and Compliance project.

A project charter should be established before significant implementation work begins. It provides a common understanding between executive sponsors, GRC teams, business stakeholders, security teams, technology teams, auditors, legal and compliance functions, and other participants.

A GRC project may involve activities such as:

```text
ISO/IEC 27001 Implementation

ISMS Establishment

Cybersecurity Framework Implementation

Enterprise Risk Assessment

Regulatory Compliance Program

NIS2 Compliance Program

DORA Compliance Program

Security Governance Transformation

GRC Platform Implementation

Third-Party Risk Management Program

Security Control Remediation

Internal Control Improvement

GRC Operating Model Development
```

The project charter should clearly identify the **business reason for the project**.

For example:

```text
Project:

ISO/IEC 27001 ISMS Implementation

Business Driver:

Establish a formal information security
management system and prepare the
organization for ISO/IEC 27001 certification.
```

Another example:

```text
Project:

GRC Platform Implementation

Business Driver:

Centralize risk, compliance, control,
assessment, evidence, and audit activities
within a single GRC platform.
```

The business driver explains why the organization is undertaking the project.

The charter should identify the **project sponsor**.

The sponsor is the executive who provides organizational support, authority, resources, and escalation assistance.

For example:

```text
Executive Sponsor:

Chief Information Security Officer

Project Owner:

GRC Director

Project Manager:

GRC Program Manager
```

The sponsor should have sufficient authority to resolve major organizational barriers.

The charter should identify the **GRC project manager** or project lead.

The project manager coordinates:

```text
Planning

Resources

Activities

Dependencies

Risks

Issues

Stakeholders

Deliverables

Schedule

Budget

Reporting
```

The GRC project manager does not necessarily need to be the technical expert for every area. Their primary responsibility is to ensure that the project is properly coordinated and governed.

The charter should identify the **project objectives**.

Objectives should be specific and measurable where possible.

For example:

```text
Objective 1:

Establish an enterprise ISMS.

Objective 2:

Complete the information security
risk assessment.

Objective 3:

Define applicable security controls.

Objective 4:

Develop required policies and procedures.

Objective 5:

Implement the required controls.

Objective 6:

Complete internal audit activities.

Objective 7:

Prepare the organization for certification.
```

For a GRC platform implementation:

```text
Objective 1:

Centralize enterprise risk management.

Objective 2:

Centralize compliance requirements.

Objective 3:

Automate control assessments.

Objective 4:

Centralize evidence management.

Objective 5:

Improve management reporting.

Objective 6:

Reduce manual GRC activities.
```

The charter should distinguish between **objectives and deliverables**.

An objective describes what the project intends to achieve.

A deliverable is a tangible output produced by the project.

For example:

```text
Objective:

Improve cybersecurity risk visibility.

Deliverable:

Enterprise Cybersecurity Risk Register.
```

Another example:

```text
Objective:

Improve control monitoring.

Deliverable:

Control Assessment Framework.
```

The project charter should define the **project scope**.

Scope should identify what is included in the project.

For example:

```text
In Scope:

Corporate Information Systems

Critical Business Applications

Information Security Policies

Risk Management

Security Controls

Compliance Requirements

Internal Audit

Security Governance
```

Scope should also identify what is excluded.

```text
Out of Scope:

Physical Security Operations

Non-Corporate Subsidiaries

Personal Systems

Legacy Applications Scheduled
for Decommissioning
```

Clearly defined boundaries reduce scope confusion.

The charter should define the **organizational scope**.

For example:

```text
Business Units:

Corporate

Finance

Human Resources

Technology

Operations

Sales
```

It may also identify geographical scope:

```text
Locations:

Spain

France

Germany

Italy
```

The project should specify whether the scope applies to:

```text
Entire Organization

Specific Business Units

Specific Locations

Specific Information Systems

Specific Products

Specific Services
```

The charter should define the **technology scope** where relevant.

For example:

```text
Applications

Cloud Services

Network Infrastructure

Endpoints

Databases

Identity Platforms

Security Platforms

Third-Party Services
```

For an ISO/IEC 27001 project, the scope should ultimately align with the formally defined ISMS scope.

The project charter should identify the **project methodology**.

Possible approaches include:

```text
Waterfall

Agile

Hybrid

Phased Implementation
```

GRC projects frequently benefit from a phased or hybrid approach.

For example:

```text
Phase 1:

Project Initiation

Phase 2:

Current-State Assessment

Phase 3:

Risk Assessment

Phase 4:

Framework and Control Design

Phase 5:

Implementation

Phase 6:

Assessment

Phase 7:

Remediation

Phase 8:

Internal Audit

Phase 9:

Management Review

Phase 10:

Continuous Improvement
```

The appropriate methodology depends on organizational complexity and project objectives.

The charter should define the **major project phases**.

A typical GRC implementation may follow:

```text
Initiate
   ↓
Assess
   ↓
Plan
   ↓
Design
   ↓
Implement
   ↓
Validate
   ↓
Remediate
   ↓
Report
   ↓
Transition
```

Each phase should have defined outputs.

For example:

```text
Initiate
→ Approved Project Charter

Assess
→ Current-State Assessment

Plan
→ Implementation Plan

Design
→ GRC Framework

Implement
→ Implemented Controls

Validate
→ Assessment Results

Remediate
→ Closed Findings

Report
→ Management Report

Transition
→ Operational GRC Program
```

The charter should identify **key stakeholders**.

Potential stakeholders include:

```text
Executive Management

CISO

CIO

Chief Risk Officer

Compliance

Legal

Internal Audit

GRC

Information Security

IT Operations

Human Resources

Procurement

Business Unit Leaders

Data Protection / Privacy

Finance

Third-Party Management
```

Stakeholders should be classified according to their role and level of involvement.

For example:

```text
Executive Sponsor:

Decision Authority

GRC Director:

Program Ownership

GRC Team:

Execution

Control Owners:

Control Implementation

Risk Owners:

Risk Decisions

Internal Audit:

Independent Assurance

IT:

Technical Implementation

Business Units:

Business Process Ownership
```

The charter should establish **project governance**.

A simple structure can be:

```text
Executive Sponsor
        |
Steering Committee
        |
Project Manager
        |
+-------+-------+-------+
|       |       |       |
GRC    IT    Security  Business
```

The steering committee provides direction for major decisions.

The project manager coordinates day-to-day implementation.

The GRC team manages governance, risk, compliance, control, and assurance activities.

The charter should define the **steering committee responsibilities**.

These may include:

```text
Strategic Direction

Major Decisions

Budget Decisions

Scope Changes

Risk Escalation

Issue Escalation

Resource Escalation

Project Performance Review
```

The steering committee should not become involved in every operational task.

The project charter should define **decision-making authority**.

For example:

```text
Project Manager:

Operational Decisions

GRC Director:

GRC Design Decisions

Steering Committee:

Major Scope and Resource Decisions

Executive Sponsor:

Strategic Decisions
```

This prevents delays caused by unclear authority.

The charter should define the **project governance cadence**.

For example:

```text
Daily:

Project Team Coordination

Weekly:

Project Status Meeting

Monthly:

Steering Committee

Quarterly:

Executive Review
```

The actual frequency should be based on project complexity.

The charter should define the **project deliverables**.

A GRC project may produce:

```text
Project Charter

Current-State Assessment

Risk Register

Risk Assessment

Control Framework

Policy Framework

Compliance Register

Statement of Applicability

Control Assessment Results

Evidence Repository

Gap Analysis

Remediation Plan

Audit Plan

Audit Findings

Management Report

GRC Operating Model
```

Each deliverable should have an owner and acceptance criteria.

For example:

```text
Deliverable:

Enterprise Risk Register

Owner:

GRC Manager

Approver:

Chief Risk Officer

Acceptance Criteria:

All defined business units assessed

All identified risks assigned owners

Risk ratings validated

Treatment decisions documented
```

The charter should define **project milestones**.

For example:

```text
Milestone 1:

Project Charter Approved

Milestone 2:

Scope Approved

Milestone 3:

Current-State Assessment Completed

Milestone 4:

Risk Assessment Completed

Milestone 5:

Control Framework Approved

Milestone 6:

Implementation Completed

Milestone 7:

Internal Assessment Completed

Milestone 8:

Remediation Completed

Milestone 9:

Management Review Completed
```

Milestones should represent meaningful achievements rather than simply calendar dates.

The charter should define the **project schedule**.

A high-level schedule may look like:

```text
Month 1:

Initiation and Planning

Month 2:

Current-State Assessment

Month 3:

Risk Assessment

Month 4–5:

Control Design

Month 6–8:

Implementation

Month 9:

Control Assessment

Month 10:

Remediation

Month 11:

Internal Audit

Month 12:

Management Review and Transition
```

The actual schedule should be based on organizational complexity and available resources.

The charter should identify **project dependencies**.

Dependencies may include:

```text
Availability of Subject Matter Experts

Technology Implementation

Procurement

Legal Review

Regulatory Interpretation

Third-Party Support

Data Availability

Management Approval

System Integration

Resource Availability
```

For example:

```text
GRC Platform Implementation
        ↓
Depends On
        ↓
Identity Integration
        ↓
Depends On
        ↓
IAM API Availability
```

A dependency that is not managed may become a project risk.

The charter should define **project assumptions**.

Examples include:

```text
Business Units Will Provide Required Information

Control Owners Will Participate

Required Technology Will Be Available

Management Will Provide Necessary Support

Required Resources Will Be Assigned

Stakeholders Will Participate in Assessments
```

Assumptions should be documented because incorrect assumptions can affect project delivery.

The charter should also identify **project constraints**.

Examples include:

```text
Limited Budget

Limited Resources

Fixed Deadline

Legacy Technology

Regulatory Deadline

Limited Subject Matter Expertise

Multiple Geographic Locations

Existing Transformation Projects
```

Constraints should be considered when developing the project plan.

The charter should define the **project budget** where applicable.

Budget categories may include:

```text
Personnel

Consulting

Technology

GRC Platform Licensing

Training

Certification

External Audit

Implementation Services

Travel

Contingency
```

The budget should be monitored throughout the project.

The charter should define **resource requirements**.

Resources may include:

```text
GRC Professionals

Cybersecurity Professionals

IT Engineers

Compliance Specialists

Privacy Specialists

Legal Counsel

Internal Auditors

Project Managers

Business Subject Matter Experts

External Consultants
```

The project should identify both full-time and part-time resource requirements.

The charter should identify **skills required for the project**.

For example:

```text
ISO/IEC 27001

Risk Management

Cybersecurity

Compliance

Privacy

Internal Audit

Project Management

Technology Architecture

Cloud Security

Third-Party Risk
```

Where internal capabilities are insufficient, external expertise may be required.

The charter should establish **project success criteria**.

Success criteria should be measurable.

For example:

```text
100% of in-scope business units assessed

100% of critical risks assigned owners

100% of mandatory policies approved

95%+ of required controls implemented

All critical findings remediated

Internal audit completed

Management approval obtained
```

The organization should avoid defining success only as "project completed."

The project should demonstrate whether the intended business outcomes were achieved.

The charter should define **quality criteria**.

For example:

```text
Risk Assessments:

Approved methodology

Consistent scoring

Documented rationale

Assigned risk owners

Control Assessments:

Defined test procedures

Traceable evidence

Documented results

Independent review where required
```

Quality requirements should be established before project deliverables are produced.

The charter should define **project reporting requirements**.

A project status report may contain:

```text
Overall Status

Milestones

Completed Activities

Upcoming Activities

Budget

Schedule

Risks

Issues

Dependencies

Decisions Required

Resource Issues

Key Achievements
```

For example:

```text
Overall Status:

GREEN

Schedule:

On Track

Budget:

Within Plan

Major Risk:

Delayed Business Unit Assessments

Decision Required:

Additional Assessment Resources
```

The charter should establish **project risk management**.

Project risks may include:

```text
Resource Shortage

Scope Creep

Management Delays

Technology Delays

Poor Data Quality

Stakeholder Resistance

Regulatory Changes

Integration Problems

Budget Overrun

Schedule Delay
```

Each significant project risk should be recorded in the project risk register.

For example:

```text
Risk:

Business Units Do Not Provide
Required Assessment Information

Likelihood:

Medium

Impact:

High

Rating:

High

Owner:

GRC Project Manager

Treatment:

Escalation and Defined Submission Deadlines
```

The project charter should distinguish between **project risks and enterprise cybersecurity risks**.

A project risk affects project delivery.

An enterprise cybersecurity risk affects organizational objectives or information assets.

For example:

```text
Project Risk:

GRC Platform Implementation Is Delayed.

Enterprise Risk:

Critical Security Control Is Not Operating.
```

The two may be related but should not automatically be treated as the same risk.

The charter should define **issue management**.

Issues are problems that have already occurred.

For example:

```text
Issue:

Business Unit Assessment Is Two Weeks Late.

Impact:

Project Milestone Delayed.

Owner:

Business Unit Manager

Action:

Escalation and Recovery Plan
```

The project should maintain separate tracking for:

```text
Risks

Issues

Actions

Decisions

Dependencies
```

The charter should define **change control**.

Potential changes include:

```text
Scope Change

Schedule Change

Budget Change

Resource Change

Requirement Change

Technology Change

Deliverable Change
```

A typical change process is:

```text
Change Request
      ↓
Impact Assessment
      ↓
Project Manager Review
      ↓
Approval
      ↓
Implementation
      ↓
Documentation
```

Major changes should be escalated to the appropriate governance authority.

The charter should address **scope creep**.

Scope creep occurs when additional activities are added without appropriate assessment or approval.

For example:

```text
Original Scope:

ISO/IEC 27001 Implementation

Additional Request:

Full Enterprise Privacy Transformation
```

The additional request should be evaluated before being added to the project.

The project manager should determine whether it:

```text
Fits Existing Scope

Requires Additional Resources

Requires Additional Budget

Requires Schedule Extension

Should Become a Separate Project
```

The charter should define **communication requirements**.

Different stakeholders may require different information.

For example:

```text
Executive Management:

Business Impact and Strategic Status

Steering Committee:

Risks, Issues, Decisions, Milestones

Project Team:

Tasks, Dependencies, Issues

Control Owners:

Control Implementation Requirements

Internal Audit:

Evidence and Assurance Information
```

Communication should be tailored to the audience.

The charter should identify **project documentation requirements**.

Documentation may include:

```text
Project Charter

Project Plan

Meeting Minutes

Decision Log

Risk Register

Issue Register

Action Register

Change Requests

Status Reports

Deliverables

Approval Records
```

Project documentation should be maintained in an appropriately controlled repository.

The project should maintain a **decision log**.

For example:

```text
Decision ID:

DEC-017

Decision:

Adopt NIST CSF as the cybersecurity
risk management reference framework.

Date:

30 September 2026

Decision Owner:

CISO

Rationale:

Align cybersecurity risk management
with organizational objectives.
```

Decision records provide evidence of governance and accountability.

The project should also maintain an **action register**.

For example:

```text
Action ID:

ACT-045

Action:

Complete Finance Business Unit
Risk Assessment.

Owner:

Finance Security Lead

Due Date:

15 October 2026

Status:

In Progress
```

The charter should establish **approval requirements**.

Important approvals may include:

```text
Project Charter

Project Scope

Risk Methodology

Control Framework

Major Deliverables

Major Scope Changes

Final Project Closure
```

Approval authority should be clearly defined.

The charter should identify **project closure criteria**.

For example:

```text
All Deliverables Completed

Critical Project Issues Resolved

Required Approvals Obtained

Outstanding Risks Transferred

Operational Ownership Established

Documentation Completed

Lessons Learned Captured

Project Closure Approved
```

A GRC project should not simply end when the final document is produced.

The organization must ensure that ownership transitions into normal operations.

A typical transition model is:

```text
Project
   ↓
Implementation
   ↓
Validation
   ↓
Operational Handover
   ↓
Business-as-Usual GRC
   ↓
Continuous Improvement
```

The project charter should define the **operational handover**.

The handover may include:

```text
Process Documentation

Control Ownership

Risk Ownership

System Administration

Evidence Management

Reporting

Monitoring

Training

Support Procedures
```

For example:

```text
Project:

GRC Platform Implementation

Project Team:

Implements Platform

Operations:

GRC Team

System Administration:

GRC Platform Administrator

Control Ownership:

Business / Security Owners
```

The project should ensure that operational teams are prepared before handover.

The charter should also define **training requirements**.

Training may be required for:

```text
GRC Users

Control Owners

Risk Owners

System Administrators

Business Users

Management
```

Training should be appropriate to the individual's responsibilities.

The project should define **lessons learned**.

Lessons learned may address:

```text
What Worked Well

What Did Not Work

Major Challenges

Root Causes

Successful Practices

Stakeholder Engagement

Resource Planning

Technology

Governance

Recommendations
```

Lessons learned should be captured before project closure.

A GRC project charter should ultimately answer five fundamental questions:

```text
WHY?

Why is the project required?

WHAT?

What will the project deliver?

WHO?

Who owns, governs, and executes the project?

WHEN?

When will the project be completed?

HOW?

How will the project be implemented and controlled?
```

The GRC professional should verify that:

```text

Success Criteria Are Defined

Reporting Requirements Are Defined

Documentation Requirements Are Defined

Approval Requirements Are Defined

Operational Handover Is Planned

```

The key principle is:

> **A GRC project charter establishes the foundation for successful GRC implementation by clearly defining the business purpose, objectives, scope, governance, responsibilities, deliverables, resources, risks, milestones, and success criteria before execution begins.**

# 17.17 GRC Project and Implementation Templates

## Part 2 – GRC Implementation Roadmap

A GRC implementation roadmap provides a structured sequence of activities required to establish, improve, or transform an organization's Governance, Risk, and Compliance capabilities.

The roadmap converts strategic objectives into an actionable implementation plan.

A GRC roadmap should show:

```text
Current State
      ↓
Target State
      ↓
Implementation Priorities
      ↓
Projects and Initiatives
      ↓
Milestones
      ↓
Resources
      ↓
Implementation
      ↓
Validation
      ↓
Continuous Improvement
```

A roadmap should not simply be a list of activities. It should show **what needs to change, why it needs to change, when it will change, who is responsible, and how progress will be measured**.

A GRC implementation roadmap may be required for:

```text
ISO/IEC 27001 Implementation

NIST CSF Implementation

NIS2 Compliance Program

DORA Compliance Program

Enterprise GRC Transformation

GRC Platform Implementation

Cybersecurity Risk Management Improvement

Third-Party Risk Management

Internal Control Transformation

Security Governance Improvement
```

The roadmap should begin with a clear **current-state assessment**.

The current state identifies how GRC operates today.

It may assess:

```text
Governance

Policies

Risk Management

Security Controls

Compliance

Internal Audit

Third-Party Risk

Data Protection

Incident Management

Business Continuity

Security Awareness

Metrics and Reporting

GRC Technology
```

For example:

```text
CURRENT STATE

Risk Management:

Risk assessments performed inconsistently.

Risk register:

Multiple spreadsheets.

Control Management:

Controls documented but not centrally monitored.

Compliance:

Regulatory requirements tracked manually.

Evidence:

Stored across multiple repositories.

Reporting:

Manual executive reports.
```

The roadmap should then define the **target state**.

For example:

```text
TARGET STATE

Risk Management:

Standardized enterprise risk methodology.

Risk Register:

Centralized GRC platform.

Control Management:

Centralized control library and monitoring.

Compliance:

Automated regulatory requirement tracking.

Evidence:

Centralized evidence repository.

Reporting:

Automated executive dashboards.
```

The difference between the current and target states creates the **implementation gap**.

```text
Current State
      ↓
Gap Analysis
      ↓
Target State
```

The roadmap should identify the major **GRC capability areas**.

A typical capability model includes:

```text
GRC Governance

Risk Management

Control Management

Compliance Management

Audit Management

Third-Party Risk

Policy Management

Issue Management

Evidence Management

Metrics and Reporting

GRC Technology

Data Management
```

Each capability should have a defined maturity or target state.

For example:

```text
Capability:

Risk Management

Current:

Level 2 – Developing

Target:

Level 4 – Managed
```

The roadmap should establish **implementation priorities**.

Not every GRC improvement needs to happen at the same time.

Prioritization should consider:

```text
Regulatory Requirements

Business Risk

Security Risk

Customer Requirements

Audit Findings

Control Weaknesses

Management Priorities

Technology Dependencies

Resource Availability

Implementation Complexity
```

A high-risk regulatory requirement may therefore receive a higher priority than a low-impact process improvement.

A practical prioritization model is:

```text
Priority 1:

Regulatory / Critical Risk

Priority 2:

High-Risk Control Gaps

Priority 3:

Operational Improvements

Priority 4:

Optimization
```

The roadmap should identify **quick wins**.

Quick wins are improvements that can be implemented relatively quickly while providing meaningful value.

Examples include:

```text
Standardizing Risk Categories

Creating a Central Risk Register

Defining Control Ownership

Establishing a Compliance Obligations Register

Standardizing Evidence Naming

Creating a GRC Dashboard

Establishing a GRC Governance Committee
```

Quick wins can demonstrate value while larger transformation initiatives are being planned.

The roadmap should also identify **strategic initiatives**.

Examples include:

```text
GRC Platform Implementation

Enterprise Risk Transformation

Control Automation

Regulatory Compliance Automation

Third-Party Risk Management Program

Integrated Security Metrics Program
```

The roadmap should distinguish between:

```text
Quick Wins
      +
Tactical Improvements
      +
Strategic Initiatives
      =
GRC Transformation
```

The roadmap should define **implementation phases**.

A typical GRC implementation can be structured as:

```text
Phase 1 – Initiate

Phase 2 – Assess

Phase 3 – Design

Phase 4 – Prioritize

Phase 5 – Implement

Phase 6 – Validate

Phase 7 – Remediate

Phase 8 – Transition

Phase 9 – Improve
```

### Phase 1 – Initiate

The initiation phase establishes the foundation.

Activities may include:

```text
Define Business Drivers

Identify Executive Sponsor

Define Project Governance

Establish Project Team

Define Scope

Approve Project Charter

Identify Stakeholders

Establish Communication Plan
```

Primary outputs:

```text
Approved Project Charter

Governance Structure

Initial Project Plan

Stakeholder Register
```

### Phase 2 – Assess

The assessment phase establishes the current state.

Activities may include:

```text
GRC Maturity Assessment

Risk Assessment

Compliance Assessment

Control Assessment

Policy Review

Process Assessment

Technology Assessment

Stakeholder Interviews
```

Primary outputs:

```text
Current-State Assessment

Risk Register

Compliance Gap Analysis

Control Gap Analysis

GRC Maturity Assessment
```

### Phase 3 – Design

The organization defines the target operating model.

Activities may include:

```text
GRC Operating Model

Governance Structure

Risk Methodology

Control Framework

Compliance Process

Assessment Methodology

Evidence Management

Reporting Model

GRC Technology Architecture
```

Primary outputs:

```text
Target Operating Model

GRC Framework

Process Designs

Control Framework

Technology Requirements
```

### Phase 4 – Prioritize

The organization determines what should be implemented first.

Activities include:

```text
Risk-Based Prioritization

Regulatory Prioritization

Control Gap Prioritization

Resource Assessment

Dependency Analysis

Cost-Benefit Analysis
```

Primary output:

```text
Prioritized GRC Implementation Backlog
```

### Phase 5 – Implement

The organization implements the required changes.

Activities may include:

```text
Policy Development

Control Implementation

Risk Process Implementation

Compliance Process Implementation

GRC Platform Configuration

Workflow Implementation

Evidence Repository Implementation

Dashboard Development

User Training
```

Primary outputs:

```text
Implemented Processes

Implemented Controls

Configured GRC Platform

Training Materials

Operational Procedures
```

### Phase 6 – Validate

The organization determines whether implementation is working as intended.

Activities include:

```text
Control Testing

Process Testing

Configuration Review

Evidence Validation

User Acceptance Testing

Compliance Assessment

Internal Review
```

Primary outputs:

```text
Validation Results

Control Assessment Results

Testing Evidence

Identified Issues
```

### Phase 7 – Remediate

Identified weaknesses are addressed.

Activities include:

```text
Finding Management

Corrective Actions

Risk Treatment

Control Improvements

Process Improvements

Policy Updates
```

Primary outputs:

```text
Remediation Plan

Closed Findings

Updated Risk Register
```

# 17.17 GRC Project and Implementation Templates

## Part 3 – RACI Matrix

A RACI matrix is a responsibility assignment tool used to clearly define who performs, owns, provides input to, and receives information about activities within a GRC project or process.

RACI stands for:

```text
R – Responsible
A – Accountable
C – Consulted
I – Informed
```

The RACI matrix helps prevent unclear ownership, duplicated responsibilities, missed activities, and decision-making delays.

In GRC, unclear responsibility can create significant problems.

For example, an organization may identify a high-risk control deficiency but be unable to determine who is responsible for remediation.

A RACI matrix addresses this problem by explicitly assigning roles.

## R – Responsible

**Responsible** identifies the person or team that performs the work.

There can be more than one Responsible party for an activity when necessary.

For example:

```text
Activity:

Perform Security Control Assessment

Responsible:

GRC Assessment Team
```

The Responsible party performs the actual activity.

Examples include:

```text
Conducting Risk Assessments

Collecting Evidence

Testing Controls

Updating the Risk Register

Mapping Regulatory Requirements

Preparing Audit Documentation

Implementing Security Controls
```

## A – Accountable

**Accountable** identifies the person who ultimately owns the outcome and is answerable for completion.

There should normally be **one Accountable party for each activity**.

For example:

```text
Activity:

Approve Enterprise Risk Assessment

Accountable:

Chief Information Security Officer
```

The Accountable person does not necessarily perform the work.

The important distinction is:

```text
Responsible:
Does the work.

Accountable:
Owns the outcome.
```

For example:

```text
GRC Analyst
     ↓
Responsible for preparing assessment

GRC Manager
     ↓
Accountable for assessment completion
```

Multiple Accountable parties can create ambiguity and should generally be avoided.

## C – Consulted

**Consulted** identifies people who provide knowledge, expertise, advice, or feedback before an activity or decision is completed.

Communication with Consulted parties is generally two-way.

For example:

```text
Activity:

Develop Data Classification Policy

Responsible:

GRC Team

Accountable:

CISO

Consulted:

Privacy

Legal

Data Owners

IT
```

The Consulted parties provide relevant expertise.

Examples include:

```text
Legal

Privacy

Cybersecurity Architecture

IT Operations

Business Owners

Compliance

Internal Audit
```

## I – Informed

**Informed** identifies stakeholders who need to receive information about the activity or outcome.

Communication with Informed parties is generally one-way.

For example:

```text
Activity:

Complete Enterprise Risk Assessment

Responsible:

GRC Team

Accountable:

CRO

Consulted:

Business Risk Owners

CISO

Informed:

Executive Management
```

Informed stakeholders do not normally participate directly in the activity.

They receive relevant updates or decisions.

The four RACI roles can therefore be summarized as:

```text
R – Responsible
Who performs the work?

A – Accountable
Who owns the outcome?

C – Consulted
Who provides input?

I – Informed
Who needs to know?
```

A RACI matrix normally places **activities or deliverables in rows** and **organizational roles in columns**.

Example:

| GRC Activity        | CISO | GRC Manager | GRC Analyst | Risk Owner | IT | Internal Audit |
| ------------------- | ---- | ----------- | ----------- | ---------- | -- | -------------- |
| Risk Assessment     | A    | R           | R           | C          | C  | I              |
| Risk Treatment      | A    | R           | R           | A          | R  | I              |
| Control Assessment  | A    | R           | R           | C          | R  | I              |
| Compliance Mapping  | A    | R           | R           | C          | C  | I              |
| Internal Audit      | I    | C           | C           | C          | C  | A/R            |
| Executive Reporting | A    | R           | R           | C          | I  | I              |

The matrix should be customized to the organization's structure.

The GRC professional should avoid using individual employee names where possible.

Roles are generally more sustainable than names.

For example, use:

```text
GRC Manager
```

instead of:

```text
John Smith
```

This allows the RACI matrix to remain valid when employees change positions.

The RACI matrix should be created during project planning rather than after implementation problems occur.

A typical process is:

```text

        ↓

        ↓

        ↓

        ↓

        ↓

        ↓

```

Ask:

> Who actually performs this activity?

For example:

```text

```

The fourth step is to assign the **Accountable** role.

Ask:

> Who ultimately owns the outcome?

For example:

```text

Accountable:
```

```text
CISO

Executive Management

Internal Audit
```

The RACI matrix should be reviewed with the people who are assigned responsibilities.

This is important because an organization may assign a responsibility to a role that does not have the necessary authority, resources, or expertise.

The RACI matrix should therefore be validated.

A validation process can include:

```text
Draft RACI
     ↓
Review With Process Owners
     ↓
Review With Management
     ↓
Resolve Conflicts
     ↓
Approve
     ↓
Publish
```

The RACI matrix should identify **one clear Accountable owner** for each major activity.

For example:

```text
Correct:

Risk Assessment → A = Risk Owner
```

Avoid:

```text
Risk Assessment → A = CISO + CRO + GRC Manager
```

Multiple Accountable parties can make it unclear who has final decision authority.

The organization should distinguish between **Accountability and Responsibility**.

For example:

```text
Activity:

Implement Security Control

Responsible:

IT Security Team

Accountable:

Control Owner
```

The IT Security Team performs the implementation.

The Control Owner remains accountable for ensuring that the control achieves its intended objective.

Another example:

```text
Activity:

Risk Assessment

Responsible:

GRC Analyst

Accountable:

Risk Owner
```

The GRC Analyst facilitates and documents the assessment.

The Risk Owner remains accountable for the business risk.

This distinction is especially important in risk management.

The RACI matrix should also avoid assigning **R and A automatically to the same person**.

It is acceptable for one person to be both Responsible and Accountable when appropriate.

For example:

```text
Small Organization:

GRC Manager = R/A
```

However, in larger organizations, separating execution and accountability may provide stronger governance.

The RACI matrix should also avoid excessive use of **C**.

If every activity has many Consulted stakeholders, decision-making can become slow.

For example:

```text
Poor:

R = GRC

A = CISO

C = Legal, Privacy, HR, IT, Finance,
    Procurement, Operations, Audit,
    Business, Architecture, Compliance

I = Everyone Else
```

A better approach is to identify only stakeholders whose input is genuinely required.

The same principle applies to **Informed** stakeholders.

Not every person needs to receive every update.

Information should be distributed according to business relevance.

The RACI matrix should therefore support efficient governance rather than create unnecessary bureaucracy.

```text
→ Technical Implementation

Compliance
→ Regulatory Oversight

Internal Audit
→ Independent Assurance
```

This separation supports the principle that GRC should provide governance and oversight without unnecessarily taking ownership of operational activities.

The RACI matrix should therefore reinforce the organization's **three lines model** where applicable:

```text
First Line
→ Owns and Manages Risks

Second Line
→ Provides Risk, Compliance, and Oversight Functions

Third Line
→ Provides Independent Assurance
```

For example:

```text
First Line:

Control Owner
Business Owner
IT Operations

Second Line:

GRC
Risk
Compliance
Information Security Governance

Third Line:

Internal Audit
```

The exact structure may vary by organization.

The key principle is:

> **A RACI matrix establishes clear accountability and responsibility by defining who performs the work, who owns the outcome, who provides input, and who must be informed, thereby reducing ambiguity and strengthening GRC governance.**

# 17.17 GRC Project and Implementation Templates

## Part 4 – GRC Project Status Report

A GRC project status report provides management and project stakeholders with a concise view of project progress, achievements, upcoming activities, risks, issues, decisions, dependencies, resources, budget, and overall project health.

The status report should allow stakeholders to quickly determine:

```text
Are we on schedule?

Are we within budget?

Are the expected deliverables being completed?

Are there significant risks or issues?

Are decisions required?

Are resources sufficient?

Is the project still expected to achieve its objectives?
```

A GRC project status report should be produced regularly throughout the project lifecycle.

Typical reporting frequencies include:

```text
Weekly:
Project Team

Biweekly:
Project Management

Monthly:
Steering Committee

Quarterly:
Executive Management
```

The frequency should depend on project complexity, risk, and governance requirements.

The status report should begin with an **overall project status**.

A simple status model is:

```text
GREEN
Project is on track.

AMBER
Project requires management attention.

RED
Project has a significant issue or deviation
requiring escalation.
```

Example:

```text
Overall Status:

AMBER

Reason:

Two major control implementation activities
are delayed and may affect the planned
assessment milestone.
```

The overall status should reflect the actual health of the project rather than simply the opinion of the project manager.

A project status report should include the **project name**.

Example:

```text
Project:

Enterprise GRC Transformation
```

It should also identify the:

```text
Project Sponsor

Project Manager

Reporting Period

Report Date

Project Phase

Overall Status
```

Example:

```text
Project:

ISO/IEC 27001 Implementation

Sponsor:

CISO

Project Manager:

GRC Program Manager

Reporting Period:

01–31 January 2027

Current Phase:

Control Implementation

Overall Status:

GREEN
```

The status report should provide an **executive summary**.

The executive summary should describe the most important developments during the reporting period.

Example:

```text
The project remains on schedule.

Risk assessment activities have been completed
for all in-scope business units.

Security control implementation is 82% complete.

Three high-priority remediation activities
remain outstanding.

No budget overrun is currently forecast.
```

The executive summary should focus on information that management needs to know.

It should avoid excessive operational detail.

The report should summarize **key achievements**.

Examples include:

```text
Risk Assessment Completed

Control Framework Approved

Security Policies Approved

GRC Platform Configuration Completed

Business Unit Assessments Completed

Critical Findings Remediated

Internal Audit Completed
```

Example:

```text
Key Achievements:

• Completed enterprise risk assessment.
• Approved information security policy.
• Completed 80% of control implementation.
• Completed GRC platform user acceptance testing.
```

The report should identify **activities completed during the reporting period**.

Example:

```text
Completed Activities:

1. Finance risk assessment.

2. HR control assessment.

3. Access control remediation.

4. GRC platform workflow testing.

5. Management reporting configuration.
```

The report should identify **planned activities for the next reporting period**.

Example:

```text
Next Period:

1. Complete remaining control implementations.

2. Perform control effectiveness testing.

3. Remediate critical findings.

4. Conduct management review preparation.

5. Finalize internal audit schedule.
```

The report should track **project milestones**.

Example:

| Milestone              | Planned Date | Actual / Forecast Date | Status   |
| ---------------------- | ------------ | ---------------------- | -------- |
| Project Charter        | Jan 2027     | Jan 2027               | Complete |
| Risk Assessment        | Mar 2027     | Mar 2027               | Complete |
| Control Design         | May 2027     | May 2027               | Complete |
| Control Implementation | Aug 2027     | Sep 2027               | Amber    |
| Internal Audit         | Oct 2027     | Oct 2027               | On Track |
| Project Closure        | Dec 2027     | Dec 2027               | On Track |

Milestones should show whether important project objectives are being achieved.

The status report should track **deliverables**.

Example:

| Deliverable                | Owner          | Target Date | Status      |
| -------------------------- | -------------- | ----------- | ----------- |
| Risk Register              | GRC            | Mar 2027    | Complete    |
| Statement of Applicability | GRC            | May 2027    | Complete    |
| Security Procedures        | Security       | Jun 2027    | In Progress |
| Control Evidence           | Control Owners | Aug 2027    | In Progress |
| Internal Audit Report      | Internal Audit | Oct 2027    | Not Started |

The status should use consistent terminology.

For example:

```text
Not Started

In Progress

Complete

Delayed

Blocked

Cancelled
```

The report should include **schedule status**.

Example:

```text
Planned Completion:

31 December 2027

Current Forecast:

15 January 2028

Schedule Variance:

15 Days

Status:

AMBER
```

The project manager should explain the reason for significant schedule variance.

For example:

```text
Cause:

Delayed availability of business subject
matter experts.

Impact:

Control testing delayed by two weeks.

Action:

Additional assessment resources assigned.
```

The status report should include **budget status**.

Example:

```text
Approved Budget:

€1,200,000

Actual Spend:

€740,000

Remaining Budget:

€460,000

Forecast Final Cost:

€1,150,000

Status:

GREEN
```

Budget information should be presented at a level appropriate to the audience.

Executive management may require summary figures, while the project team may require detailed cost information.

The report should include **resource status**.

Example:

```text
Planned Resources:

18

Current Resources:

16

Resource Gap:

2

Impact:

Control assessment activities delayed.
```

Resource issues should be escalated when they threaten project objectives.

The report should identify **project risks**.

A project risk is an uncertain event that may affect project objectives.

Example:

| Risk                      | Likelihood | Impact | Rating | Owner           | Treatment                    |
| ------------------------- | ---------- | ------ | ------ | --------------- | ---------------------------- |
| Business SMEs unavailable | Medium     | High   | High   | Project Manager | Escalate resource allocation |
| Integration delay         | Medium     | High   | High   | IT Lead         | Accelerate technical testing |
| Scope expansion           | Low        | High   | Medium | Sponsor         | Enforce change control       |

The report should focus on significant project risks rather than reproducing the entire project risk register.

The report should identify **project issues**.

An issue is a problem that has already occurred.

Example:

```text
Issue:

GRC platform integration has failed during
user acceptance testing.

Impact:

Production deployment delayed.

Owner:

IT Project Lead

Target Resolution:

15 September 2027

Status:

In Progress
```

High-impact issues should be escalated promptly.

The report should distinguish clearly between:

```text
Risk:
Something that may happen.

Issue:
Something that has happened.

Action:
Something that needs to be done.

Decision:
Something that requires an authorized choice.
```

The report should include **actions**.

Example:

| Action                             | Owner    | Due Date | Status      |
| ---------------------------------- | -------- | -------- | ----------- |
| Complete Finance control testing   | GRC Lead | 10 Sep   | In Progress |
| Resolve platform integration issue | IT Lead  | 12 Sep   | In Progress |
| Approve risk treatment plan        | CISO     | 15 Sep   | Pending     |

Actions should have clear owners and due dates.

The report should identify **decisions required from management**.

Example:

```text
Decision Required:

Approve additional two FTEs for control testing.

Reason:

Current resources cannot complete testing
within the approved schedule.

Decision Owner:

Steering Committee

Required By:

20 September 2027
```

This is one of the most important functions of a project status report.

Management should not have to search through multiple pages to identify decisions requiring action.

Examples include:

```text

30 September 2027
```

```text
Pending Steering Committee
```

Examples:


Common GRC project status-reporting mistakes include:

```text
Reporting Activities Without Outcomes

Hiding Delays

Reporting GREEN When Major Risks Exist

Failing to Identify Decision Requirements

Reporting Risks Without Owners

Reporting Issues Without Actions

Using Outdated Information

Not Tracking Budget

Not Tracking Resource Constraints

Ignoring Scope Changes

Providing Excessive Technical Detail to Executives

Failing to Escalate Critical Problems

Using Different Status Definitions

Creating Reports Manually From Multiple Sources

Not Maintaining Historical Reports
```

The status report should be **transparent**.

If a project is behind schedule, the report should say so.

If the project is over budget, the report should say so.

If a critical dependency is blocking implementation, the report should identify it.

Accurate reporting enables management to intervene before problems become major failures.

The status report should also provide a **forward-looking forecast**.

For example:

```text

AMBER

Expected Completion:

15 December 2027

Forecast:

Project expected to complete within
approved budget with a two-week
schedule extension.
```

A forecast is more useful than simply reporting historical performance.

The key principle is:

> **A GRC project status report provides transparent, structured, and decision-oriented information about project health, progress, risks, issues, resources, budget, schedule, and expected outcomes so that stakeholders can take timely corrective action and maintain effective project governance.**
