# 20.17 GRC Tools and Templates Terms

This section defines the core terminology associated with **GRC Tools, GRC Platforms, Governance Documentation, Risk Registers, Compliance Registers, Control Libraries, Assessment Templates, Audit Workpapers, Dashboards, Evidence Management, Workflow, Reporting, and GRC Automation**.

> **Terminology note:** This glossary is designed for the GRC knowledge base and supports practical work across **ISO 27001, ISO 31000, ISO 22301, ISO 42001, NIST CSF, COBIT, GDPR, PCI DSS, DORA, NIS2, third-party risk, audit, risk management, and cybersecurity governance**.

---

# GRC Tools and Templates Glossary

| Term                                        | Definition                                                                                                                                                |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **GRC Tool**                                | Software or technology used to support governance, risk management, compliance, audit, controls, evidence, reporting, and related GRC activities.         |
| **GRC Platform**                            | Integrated technology platform providing multiple GRC capabilities through a common architecture, data model, workflows, and reporting environment.       |
| **GRC Solution**                            | Technology-based solution used to manage one or more governance, risk, compliance, audit, security, or privacy processes.                                 |
| **Integrated GRC**                          | Approach in which governance, risk, compliance, audit, controls, policies, and related information are managed through connected processes and systems.   |
| **Enterprise GRC (eGRC)**                   | Enterprise-wide approach to integrating governance, risk, compliance, controls, assessments, and reporting.                                               |
| **GRC Technology**                          | Technologies used to automate, manage, analyze, and report GRC processes and information.                                                                 |
| **GRC Architecture**                        | Structure defining how GRC processes, data, applications, integrations, workflows, controls, and reporting capabilities are organized.                    |
| **GRC Operating Model**                     | Defined structure for how GRC responsibilities, processes, technology, governance, and decision-making operate within an organization.                    |
| **GRC Workflow**                            | Defined sequence of activities, approvals, decisions, notifications, and actions used to execute a GRC process.                                           |
| **Workflow Automation**                     | Use of technology to automatically execute repetitive GRC activities according to predefined rules.                                                       |
| **GRC Automation**                          | Application of automation technologies to GRC processes such as assessments, approvals, evidence collection, issue management, and reporting.             |
| **GRC Orchestration**                       | Coordination of multiple systems, workflows, data sources, and actions to execute an end-to-end GRC process.                                              |
| **GRC Integration**                         | Connection between GRC platforms and other enterprise systems to exchange information or trigger workflows.                                               |
| **GRC API**                                 | Application programming interface used to exchange GRC information between systems.                                                                       |
| **GRC Data Model**                          | Structured representation of entities, relationships, attributes, and dependencies within a GRC platform.                                                 |
| **GRC Repository**                          | Centralized location for storing GRC records, documents, controls, risks, assessments, evidence, and related information.                                 |
| **GRC Database**                            | Structured data store containing GRC records and relationships.                                                                                           |
| **GRC Portal**                              | User-facing interface through which personnel access GRC processes, forms, dashboards, workflows, and information.                                        |
| **GRC Workspace**                           | Dedicated environment within a GRC platform for managing a specific GRC activity, function, business unit, or program.                                    |
| **GRC Module**                              | Functional component of a GRC platform dedicated to a specific capability such as risk, compliance, audit, or third-party risk.                           |
| **Risk Module**                             | GRC platform component used to identify, assess, treat, monitor, and report risks.                                                                        |
| **Compliance Module**                       | GRC platform component used to manage obligations, requirements, controls, assessments, evidence, and compliance status.                                  |
| **Audit Module**                            | GRC platform component supporting audit planning, execution, workpapers, findings, evidence, and remediation.                                             |
| **Policy Module**                           | GRC capability used to create, approve, publish, acknowledge, and manage policies.                                                                        |
| **Third-Party Risk Module**                 | GRC capability used to assess, monitor, and manage supplier and third-party risks.                                                                        |
| **Issue Management Module**                 | GRC capability used to record, assign, track, remediate, validate, and close issues and findings.                                                         |
| **Business Continuity Module**              | GRC capability supporting business impact analysis, continuity planning, exercises, dependencies, and recovery management.                                |
| **Privacy Module**                          | GRC capability supporting privacy assessments, data inventories, DPIAs, DSARs, privacy risks, and compliance activities.                                  |
| **Cyber Risk Module**                       | GRC capability focused on cybersecurity risk identification, assessment, treatment, monitoring, and reporting.                                            |
| **AI Governance Module**                    | GRC capability supporting AI inventories, AI risk assessments, AI controls, governance requirements, and AI system oversight.                             |
| **Control Management Module**               | GRC capability used to manage control definitions, ownership, testing, evidence, effectiveness, and remediation.                                          |
| **Integrated Risk Management (IRM)**        | Approach that connects different risk disciplines, including cybersecurity, operational, financial, compliance, third-party, privacy, and strategic risk. |
| **IRM Platform**                            | Technology platform designed to provide integrated management of multiple enterprise risk domains.                                                        |
| **Risk Register**                           | Structured record of identified risks, their causes, consequences, owners, ratings, treatments, and status.                                               |
| **Enterprise Risk Register**                | Consolidated repository of significant risks across an organization.                                                                                      |
| **Cybersecurity Risk Register**             | Register containing identified cybersecurity risks and their assessments, owners, treatments, and status.                                                 |
| **Compliance Risk Register**                | Register of risks arising from potential failure to meet applicable laws, regulations, standards, contracts, or policies.                                 |
| **Privacy Risk Register**                   | Register containing identified privacy risks and associated treatments and owners.                                                                        |
| **Third-Party Risk Register**               | Register containing risks associated with suppliers, vendors, partners, and other external parties.                                                       |
| **Risk Record**                             | Individual record representing a specific identified risk.                                                                                                |
| **Risk Statement**                          | Formal description of a risk, generally expressing the potential event, cause, and consequence.                                                           |
| **Risk Scenario**                           | Defined scenario describing how a threat, vulnerability, event, or condition could result in an undesirable outcome.                                      |
| **Risk Cause**                              | Condition, weakness, threat, or factor that could contribute to a risk occurring.                                                                         |
| **Risk Consequence**                        | Potential outcome or impact resulting from a risk event.                                                                                                  |
| **Risk Owner**                              | Person accountable for managing an identified risk.                                                                                                       |
| **Risk Assessor**                           | Person responsible for conducting or supporting a risk assessment.                                                                                        |
| **Risk Treatment Owner**                    | Person accountable for implementing a risk treatment or mitigation plan.                                                                                  |
| **Risk Acceptance Authority**               | Person or body authorized to formally accept a defined level of residual risk.                                                                            |
| **Risk Treatment Plan**                     | Document or record defining actions required to modify or manage identified risks.                                                                        |
| **Risk Mitigation Plan**                    | Plan defining actions to reduce risk likelihood, impact, or exposure.                                                                                     |
| **Risk Action**                             | Specific activity performed to address a risk.                                                                                                            |
| **Risk Treatment Tracker**                  | Tool used to monitor progress of risk treatment activities.                                                                                               |
| **Risk Heat Map**                           | Visual representation of risks according to dimensions such as likelihood and impact.                                                                     |
| **Risk Matrix**                             | Structured matrix used to determine risk ratings based on defined criteria.                                                                               |
| **Risk Appetite Statement**                 | Formal statement defining the amount and type of risk an organization is willing to accept.                                                               |
| **Risk Tolerance**                          | Acceptable variation around defined risk objectives, thresholds, or appetite.                                                                             |
| **Risk Threshold**                          | Defined point at which risk requires escalation, treatment, or additional management attention.                                                           |
| **Residual Risk**                           | Risk remaining after controls or risk treatments have been implemented.                                                                                   |
| **Inherent Risk**                           | Level of risk before considering the effect of controls or other treatments.                                                                              |
| **Target Risk**                             | Desired level of risk after planned treatments are implemented.                                                                                           |
| **Risk Score**                              | Numerical or qualitative representation of risk based on defined assessment criteria.                                                                     |
| **Risk Rating**                             | Classification assigned to a risk based on its assessed characteristics.                                                                                  |
| **Risk Trend**                              | Direction in which a risk's exposure is changing over time.                                                                                               |
| **Risk Dashboard**                          | Visual display of key risk information, trends, metrics, and exceptions.                                                                                  |
| **Risk Aggregation**                        | Combining multiple individual risks to understand overall or portfolio-level exposure.                                                                    |
| **Risk Correlation**                        | Relationship between risks where the occurrence or change of one risk may affect another.                                                                 |
| **Risk Concentration**                      | Accumulation of multiple risks around a common asset, supplier, geography, technology, process, or dependency.                                            |
| **Control**                                 | Measure designed to modify risk, prevent undesirable events, detect problems, or support achievement of objectives.                                       |
| **Control Library**                         | Centralized collection of defined controls used across an organization.                                                                                   |
| **Control Framework**                       | Structured set of controls organized around defined objectives, requirements, or risk areas.                                                              |
| **Control Objective**                       | Desired outcome that a control or group of controls is intended to achieve.                                                                               |
| **Control Description**                     | Documented explanation of what a control does, why it exists, and how it operates.                                                                        |
| **Control Owner**                           | Person accountable for implementing and maintaining a control.                                                                                            |
| **Control Operator**                        | Person responsible for performing a control activity.                                                                                                     |
| **Control Reviewer**                        | Person responsible for reviewing control execution or evidence.                                                                                           |
| **Control Frequency**                       | Frequency with which a control is performed.                                                                                                              |
| **Control Type**                            | Classification of a control, such as preventive, detective, corrective, directive, or compensating.                                                       |
| **Preventive Control**                      | Control intended to prevent an unwanted event or condition from occurring.                                                                                |
| **Detective Control**                       | Control intended to identify an unwanted event or condition after or while it occurs.                                                                     |
| **Corrective Control**                      | Control intended to correct or recover from an identified problem or incident.                                                                            |
| **Directive Control**                       | Control designed to guide or require desired behavior or actions.                                                                                         |
| **Compensating Control**                    | Alternative control used to provide equivalent or sufficient protection when a primary control cannot be implemented.                                     |
| **Automated Control**                       | Control performed primarily by technology without routine human intervention.                                                                             |
| **Manual Control**                          | Control performed primarily by people.                                                                                                                    |
| **IT-Dependent Manual Control**             | Manual control that relies on information or output generated by an IT system.                                                                            |
| **Key Control**                             | Control considered particularly important for managing significant risks or achieving critical objectives.                                                |
| **Critical Control**                        | Control whose failure could result in significant risk exposure or compliance impact.                                                                     |
| **Control Dependency**                      | Relationship in which one control relies on another control to operate effectively.                                                                       |
| **Control Objective Mapping**               | Relationship between a control and the objective it is intended to achieve.                                                                               |
| **Control-to-Risk Mapping**                 | Mapping that identifies which risks are addressed by each control.                                                                                        |
| **Control-to-Requirement Mapping**          | Mapping connecting controls to laws, regulations, standards, contractual obligations, or policies.                                                        |
| **Control-to-Framework Mapping**            | Mapping of controls to frameworks such as ISO 27001, NIST CSF, COBIT, PCI DSS, or CIS Controls.                                                           |
| **Control Crosswalk**                       | Mapping between equivalent or related controls across different frameworks or standards.                                                                  |
| **Control Harmonization**                   | Process of aligning controls from multiple frameworks to reduce duplication and improve consistency.                                                      |
| **Common Control**                          | Control implemented once and relied upon by multiple systems, processes, or compliance requirements.                                                      |
| **Inherited Control**                       | Control provided by another system, service, platform, parent organization, or external provider and relied upon by the organization.                     |
| **Shared Control**                          | Control responsibility shared between multiple organizational or external parties.                                                                        |
| **Control Baseline**                        | Defined minimum set of controls required for a system, process, environment, or risk category.                                                            |
| **Control Set**                             | Collection of controls addressing a defined objective, framework, risk, or compliance requirement.                                                        |
| **Control Testing**                         | Process of evaluating whether controls are properly designed and operating effectively.                                                                   |
| **Control Test Plan**                       | Document defining the scope, procedures, criteria, evidence, and methodology for control testing.                                                         |
| **Test of Design (ToD)**                    | Assessment of whether a control is appropriately designed to address its intended risk or requirement.                                                    |
| **Test of Operating Effectiveness (ToOE)**  | Assessment of whether a control operates effectively over a defined period.                                                                               |
| **Control Effectiveness**                   | Degree to which a control operates as intended and appropriately manages its associated risk.                                                             |
| **Control Deficiency**                      | Condition in which a control is missing, poorly designed, inconsistently implemented, or ineffective.                                                     |
| **Control Failure**                         | Instance in which a control does not operate as required or expected.                                                                                     |
| **Control Gap**                             | Difference between required control capability and current control implementation.                                                                        |
| **Control Maturity**                        | Degree to which a control is defined, implemented, managed, measured, and optimized.                                                                      |
| **Control Evidence**                        | Documentation or information demonstrating that a control exists and/or operated as required.                                                             |
| **Evidence Request**                        | Formal request for documentation or information needed to demonstrate control operation or compliance.                                                    |
| **Evidence Repository**                     | Centralized location for storing audit, control, compliance, risk, and assessment evidence.                                                               |
| **Evidence Owner**                          | Person responsible for providing or maintaining evidence associated with a control or requirement.                                                        |
| **Evidence Collection**                     | Process of gathering information demonstrating control implementation or operation.                                                                       |
| **Evidence Validation**                     | Process of confirming that evidence is relevant, complete, authentic, and sufficient.                                                                     |

| **Evidence Retention**                      | Defined period for maintaining GRC evidence.                                                                                                              |
| **Evidence Aging**                          | Period since evidence was generated or collected.                                                                                                         |

| **Evidence Traceability**                   | Ability to trace evidence to a control, requirement, system, owner, activity, and assessment.                                                             |

| **Legal Requirement**                       | Mandatory requirement established by applicable law.                                                                                                      |
| **Compliance Requirement**                  | Requirement against which organizational compliance can be assessed.                                                                                      |
| **Requirement Library**                     | Centralized repository of legal, regulatory, contractual, policy, and framework requirements.                                                             |
| **Regulatory Change Management**            | Process for identifying, assessing, implementing, and monitoring changes to applicable laws, regulations, and requirements.                               |
| **Compliance Assessment**                   | Evaluation of whether an organization, process, system, or control meets defined requirements.                                                            |

| **Compliance Status**                       | Current state of an organization's compliance with a defined requirement.                                                                                 |

| **Obligation Mapping**                      | Mapping of legal, regulatory, contractual, and policy obligations to organizational processes and controls.                                               |

| **Framework Library**                       | Repository containing frameworks, standards, controls, requirements, and related mappings.                                                                |
| **Framework Mapping**                       | Association between elements of different frameworks, standards, regulations, or control sets.                                                            |
| **Crosswalk**                               | Structured mapping showing relationships between requirements or controls across frameworks.                                                              |
| **Master Control Set**                      | Consolidated set of organizational controls used as a common baseline across multiple frameworks.                                                         |
| **Common Control Framework (CCF)**          | Unified control framework designed to satisfy requirements from multiple standards, regulations, and frameworks.                                          |
| **Control Normalization**                   | Process of representing similar controls from different frameworks in a common structure.                                                                 |

# GRC Tool vs. GRC Framework

These concepts should not be confused.

### GRC Framework

Defines:

> **What should be governed, managed, assessed, and controlled.**

Examples:

* ISO 27001
* NIST CSF
* COBIT
* PCI DSS
* ISO 31000

### GRC Tool

Provides:

> **Technology to manage and automate those activities.**

For example:

**ISO 27001**

→ Requirements

→ Controls

→ Evidence

→ Assessments

→ Findings

can be managed through a **GRC platform**.

Therefore:

> **A GRC tool does not replace a GRC framework.**

# GRC Tool vs. Spreadsheet

A spreadsheet can support basic GRC activities, especially for smaller organizations.

### Spreadsheet

**Advantages**

* inexpensive;
* flexible;
* easy to start;
* familiar;
* useful for prototypes.

**Limitations**

* weak workflow;
* limited access control;
* difficult audit trail;
* duplicate data;
* manual evidence collection;
* difficult scalability;
* limited automation;
* version-control problems.

### GRC Platform

Provides:

* centralized data;
* workflow;
* approvals;
* automation;
* role-based access;
* dashboards;
* audit trails;
* integrations;
* evidence management;
* continuous monitoring;
* scalability.

A mature organization may still use spreadsheets as **supporting tools**, but critical GRC processes should generally have stronger governance and traceability.

# Key GRC Takeaway

The purpose of GRC technology is not simply to **store compliance documents**.

A mature GRC platform should create a connected system of record:

> **Requirements → Risks → Controls → Assessments → Evidence → Findings → Remediation → Validation → Reporting**

The ultimate objective is:

> **One controlled, traceable, auditable, and increasingly automated environment for managing organizational risk, compliance, controls, and governance.**

This is particularly important for a modern **GRC Consultant / Cybersecurity GRC professional**, because the value of tools such as **ServiceNow GRC, Archer, MetricStream, IBM OpenPages, OneTrust, AuditBoard, and similar platforms** comes not merely from knowing how to operate the software, but from understanding **the GRC processes and data relationships that the technology is designed to automate**.
